Frame pacing pass — 14 September 2026 (branch `perf-60fps`)

Goal: a steady 60fps in every interaction without changing features. Target hardware: mainstream desktops/laptops from about 2019 and phones from about iPhone 12 / Pixel 6. Near-invisible quality adaptation (internal supersampling, shadow-map size) was allowed; everything else had to look and behave the same.

## How it was measured

- `scripts/measure-frames.mjs` walks every interaction: idle, model drag, each zone, project hover and open, all six case pages (scroll and Next), Playground idle, collection open/next/close, palette reroll, and on mobile page scroll, Projects, a case page, Playground and About. Per scenario it records rAF interval percentiles, dropped frames against a 60fps budget, and Long Animation Frames with script attribution. `?perfAudit=1` adds render counters (shadow redraws, which casters invalidated the shadow map) and, with `FRAMES_GPU=1`, GPU time.
- Headed Chrome with the window pinned to one display (`FRAMES_WINDOW`), real pointer input for clicks, and `FRAMES_RUNS` repeats reported as medians. The measuring machine is a fanless MacBook Air (M3) shared with other apps, with a 165Hz external display and a 60Hz built-in one; single runs swing, so the report uses medians.
- `scripts/serve-static.mjs` serves `./out` with HTTP byte ranges, like GitHub Pages. `python3 -m http.server` has none; media there cannot seek, which invalidated earlier Playground numbers.
- `scripts/profile-frames.mjs` takes CPU profiles mapped to source lines (`PERF_SOURCEMAPS=1` build); `scripts/trace-frames.mjs` attributes non-script time per thread; `scripts/compare-visual.mjs` compares screenshots against a `main` build.

## What was wrong, and what changed

| Problem (evidence) | Change |
| --- | --- |
| Dragging the nav model redrew the 2048² project shadow map every frame (nav meshes counted as casters: 94/94 frames dirty). | Shadow cache considers only layer-1 casters and lights, compared numerically from a list cached per scene version. Hidden project models are made invisible, not just scaled to 0. |
| Desktop rendered offscreen at 2× by default; frames near 18ms never triggered a downgrade. | Desktop starts at 1.5×, steps down on frequent small misses, moves up to 2× only on frames under 12.5ms, and locks out a failed tier with an escalating backoff. No MSAA on the canvas (only a full-screen quad is drawn to it). |
| three.js rebuilt every lit material's program key on every pass (the nav, project and mask passes saw 2, 3 and 5 directional lights). | A zero-intensity balancing light and a dedicated mask layer give all passes the same light counts. Projects idle busy script at 4× CPU: 2470ms → 1812ms. |
| Opening a Playground collection froze the main thread ~500ms (exhaustive packing search in render). | Same search in a prebuilt Web Worker (`public/workers/`, generated by `predev`/`prebuild`), cached per ratios and size, precomputed in idle time. |
| Mobile froze ~1.9–2.5s (4× CPU) on entering Projects and on reroll: the desktop orbit layout re-ran for a gallery mobile never lays out that way, and unmemoized sections re-rendered. | Orbit layout skipped on mobile; gallery and Projects grid memoized. |
| Playground previews re-seeked ~720 times/s: a seek that did not land re-fired `canplay`, which seeked again. | The media clock only seeks to reachable times and at most once per 500ms per clip. Previews also re-encoded with a keyframe every 15 frames. |
| Case pages (Pick a side, Back in smoothly) ran at 4–15fps with every clip decoding off-screen. | Case-page loops download near the viewport and play only while visible; heavy images and YouTube embeds load lazily; case-study chunks prefetch in idle time. |
| The 3D scene, shadows and full-screen post-processing kept rendering behind opaque case-study pages (rAF callbacks ~620–770ms of every second, WebGL work inside the worst 60–100ms gaps while scrolling). | The render loop pauses once a case study fully covers the window and resumes as soon as closing starts (`lib/sceneCoverStore.ts`, verified by `scripts/check-scene-cover.mjs`). |
| DOM loops forced layout every frame (desktop and mobile nav, glow jobs) and the About photo cycle re-rendered the whole pane 4×/s. | Nav loops moved to the shared frame scheduler with batched reads, cached sizes and skipped unchanged writes; glow jobs skip layout reads when idle; photo cycles isolated. The nav silhouette is reused while nothing moves. |

## Chrome lowers the frame rate while two or more videos play

With two or more inline videos playing and no recent pointer input, Chrome subsamples the page's display link (`vsync_subsampling_factor: 2` on a 60Hz panel, every 4th vsync at 165Hz). Measured on Playground idle with the cursor parked: 1 playing video → 165fps, 2 or more → 41fps, and moving the pointer → 163fps immediately. A 1px page animation did not lift it; stream count and preview resolution (480 vs 240px) made no difference; WebKit showed no throttle (160fps with 7 playing). It affects Playground, collections and the case pages with two or more loops, including page animations that run in that state. Avoiding it would change how previews play (never two at once, or drawing them into a canvas). Decision (site owner): leave it as is. It only applies while nobody is interacting, and any input restores full rate. The harness prints these samples as `THRT`.

## Results

Final run: `FRAMES_RUNS=2` medians, headed Chrome pinned to the 165Hz display, `serve-static.mjs`, real pointer input. Desktop is 1440×900; "proxy" is the same with 4× CPU throttling (slower than the 2019-laptop target, a stress case); mobile is 390×844 at DPR 2 with 4× CPU throttling. "Before" is the first measurement of the day on `main`'s code; where a scenario only became measurable after a harness fix, the earliest valid figure is given.

| Scenario | Before | After |
| --- | --- | --- |
| Drag the model | 131fps, 15% of frames dropped, shadows redrawn every frame | 147fps, 0% dropped |
| Projects idle | 67fps, GPU p95 27ms at 2× | 82–128fps, p99 12–19ms |
| Project hover sweep | 55fps | 67–97fps, 0% dropped |
| Open a project | 60ms long frame | no long frame |
| Case pages, scrolling and Next (all six) | 3.7–60fps, 60–220ms frames | 150–165fps, no long frames (Back in smoothly: see remaining issues) |
| Case pages at 4× CPU | 60–75fps, p99 30–36ms | 155–165fps, p99 ≤12ms |
| Open a Playground collection | 505ms main-thread freeze | 160fps, no long frame |
| Enter About | 248ms long frame | 155fps, no long frame |
| Mobile: enter Projects | 2.5s freeze (4× CPU) | 156fps, one ~80ms frame |
| Mobile: palette reroll | 2.5s freeze (4× CPU) | 162fps, no long frame |
| Projects idle, busy script at 4× CPU | 2470ms per 4s | 1812ms per 4s |

Scenarios meeting the bar (≥59fps, <1% dropped, p99 ≤25ms, no frame >50ms) in the full final run: desktop 21/31 (was 10/31), proxy 13/31, mobile 10/11. That run predates pausing the scene under case studies; re-measuring the case-page, project and About scenarios afterwards (one run each) moved every case-page scroll and Next transition, and closing a project, to passing on desktop and proxy, except Back in smoothly scrolling (below). The full matrix was not re-run after that change, so these totals understate it. What still fails outside that: Chrome's multi-video throttle (Playground idle, next/close collection; accepted), first entry into Playground, and the items listed below.

Visual parity against a `main` build (same seed): 0.00–1.02% of pixels differ across landing, Projects, About, Playground, a case page and mobile; mobile is pixel-identical. The difference images in `reports/performance/visual/` show only edge anti-aliasing on the 3D models (1.5× instead of 2× supersampling), text-edge rasterisation, and video/photo frames captured at a different moment. Layout, colours and content are unchanged.

Functional checks: `check-quality-tiers`, `check-project-rendering`, `check-playground-mobile` and `check-first-entry` pass. `check-performance` (mobile preview duration), `check-playground` (ambiguous "Close collection" selector), `check-new-playground-videos` (timeout) and `check-campaign-pages` ("Offscreen loops pause", mobile) fail identically against a `main` build, so they predate this work. `scripts/test-performance-controllers.mjs` passes, including new cases for the quality controller and the seek backoff.

## Known remaining issues

- Chrome's multi-video frame-rate throttle (above): accepted as is.
- Back in smoothly still shows one or two 60–90ms frames while scrolling: its large images and ~200-frame animated WebPs decode on the raster workers as they enter the viewport (traced as `ImageDecodeTask` inside the gaps). The animated WebPs decode continuously while visible; removing that would mean changing their format.
- On one proxy run, idle Projects after returning showed twelve ~105ms frames that earlier runs did not. It has not been reproduced or attributed yet.
- First entry into Playground runs at 44–51fps with ~55ms frames while twelve previews start.
- On the 4× CPU proxy, case pages run at 60–75fps with p99 30–36ms and entering Projects has ~90ms frames. The proxy is slower than the target hardware; these are stress results.
- A single 70–85ms frame on the first project open (desktop) and on entering mobile Projects.
- Not verified on a physical iPhone or Android device; mobile numbers are Chrome emulation on a Mac.

Performance implementation and verification — 9 September 2026

The isolated production build uses `PERF_DIST_DIR=.next-performance` and port 3001. Port 3000 remains available. No deployment was performed. Existing workspace edits and original media were retained.

Measurements were taken on an Apple M3 (8 CPU cores, 24 GiB RAM), using headless Chrome and Playwright WebKit 26.4. Chrome desktop profiles use 10 Mbps download / 40 ms latency; the 390×844 phone profile uses 5 Mbps / 40 ms and 4× CPU throttling. These are browser emulations on a Mac, not measurements from an iPhone. WebKit measurements are unthrottled because Chrome’s CDP network/CPU controls are unavailable there. Cold and warm runs use a new browser context followed by a reload in that context. Each reported profile has one cold/warm pair, so differences below a few hundred milliseconds are not statistically established.

Frame-rate figures describe requestAnimationFrame cadence in headless browsers, not GPU presentation counters; WebKit can run faster than the physical display refresh rate.

“Ready” is navigation start through loader dismissal, including its 600 ms exit fade. It is a conservative proxy for navigation readiness. Raw resource timings and long-task/frame samples accompany the screenshots in this directory. The baseline’s first Projects screenshots were sometimes taken before all project assets had arrived; use the settled interaction captures to inspect models.

Implementation:

- A versioned local snapshot of 200 palettes supplies validated randomized role assignments without an external request on the HTML path. Existing server-inlined CSS prevents a first-paint palette change.
- Central navigation/environment/fonts retain priority. Project model and thumbnail blanket preloads were removed. Desktop project models warm progressively after navigation readiness, with immediate promotion when Projects is selected. Section content mounts on first visit; mobile waits for viewport classification before creating a scene. Detail layouts and developer UI use dynamic imports.
- The unused albedo target/pass/material cache is gone. Shadows are invalidated by transform/light changes; static views reuse maps. The installed Three r183 renderer converts legacy PCFSoft to PCF only during a shadow render, so caching requires the effective PCF setting to prevent shader sampler mismatches.
- Beauty/mask targets adapt together: desktop 1/1.5/2×, mobile .75/1/1.5× CSS resolution. Dither coordinates and outline distances remain in CSS pixels. Sustained slow frames lower quality, sustained headroom raises it, and an eight-second cooldown limits oscillation. Shadow maps follow the tier.
- DOM animation callbacks share one scheduler. Model-slot/card geometry is cached with resize/scroll/ancestor-style invalidation; read callbacks precede writes. Necessary geometry changes during directional entrances remain live. Static style writes are skipped. Model silhouette areas are generated offline with the same browser rasterizer; content hashes detect stale metadata.
- A single gallery media controller owns document playback listeners. Per-piece clocks survive hidden decoding, preview/detail URL changes, and background tabs. Preview cuts wait for a ready frame, prepare the next clip shortly before the cut, and retain the outgoing decoder through the 33 ms blend. Covered previews pause while every visible detail clip plays. Opened game iframes remain mounted when showing screenshots or closing/reopening the collection.
- Responsive images, video previews, dimensions/durations, and stable playback IDs are generated into a manifest. Hashed derivatives use immutable cache headers. The phone export retains only the active authored scene and its referenced data; the can-label WebP is pixel-identical to the PNG.
- Removing eager renderer compilation exposed a first-frame hotspot-cache race. Updating the centered model hierarchy before measuring rest positions preserves correct section selection.

Verification limits: no physical Safari/iPhone/Android device was available. The external itch.io game raises cross-origin/media-device restrictions in WebKit; the site’s iframe lifecycle passed, but real Safari gameplay remains unverified. Baseline WebKit screenshot capture timed out before a complete comparable baseline was saved. Synthetic quality-tier captures exercise hysteresis and rendering behavior, and must not be interpreted as hardware FPS benchmarks.
